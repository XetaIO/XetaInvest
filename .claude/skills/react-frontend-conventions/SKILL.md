# React frontend conventions (xeta_invest/frontend)

For the full architecture tree and routing table, see `frontend/README.md`
— this skill covers the SOLID/clean-code/testing discipline to apply on
top of that structure.

## Structure

```
src/app/                       composition root, query client, styles
src/routes/                    route registry
src/features/<Feature>/        api/, components/, hooks/, providers/, views/, lib/, types/
src/shared/                    api/, components/, hooks/, providers/, utils/
src/bindings/                  ts-rs generated types — never hand-edit (see below)
src/i18n/                      en/fr translations
```

## SOLID-equivalent principles for React/TS

- **SRP** — a component renders; business/data logic lives in a hook
  (follow the `useAuth`, `useTheme` pattern), not inlined in JSX. Split a
  component that both fetches, transforms, and renders non-trivial logic.

- **Dependency inversion** — dependencies come in via props/context, not
  hardcoded imports of concrete singletons. `AuthProvider`/`authContext.ts`
  and `ThemeProvider` are the existing context-based inversion points.
  For data-fetching, depend on a TanStack Query `queryOptions()` factory
  (e.g. `watchlistsQueryOptions` in
  `src/features/Watchlist/api/watchlists.ts`), not on inline `fetch` /
  `client.ts` calls scattered through components.

- **ISP** — keep prop types and hook return types narrow and focused.
  Don't pass a whole DTO down through several components when only a few
  fields are used; don't grow one hook to return many unrelated values.

## Clean code

- Naming: `PascalCase` for components/types, `camelCase` for
  functions/hooks (`use` prefix for hooks).
- Imports are relative — this repo has no `@/` alias. Don't introduce one.
- `any` is disallowed by oxlint (`typescript/no-explicit-any`), not by
  `tsconfig` strict mode — strict mode alone still allows `any`.
- Fire-and-forget navigations must be explicitly marked: `react-router`'s
  `navigate()` returns a `Promise`, so an un-awaited call outside an
  `async` chain needs `void navigate(...)` (oxlint's type-aware
  `no-floating-promises` rule enforces this).
- Prefer extraction over deeply nested JSX/conditional trees; only colocate
  a small subcomponent in the same file when it's trivial and single-use.

## Generated bindings — never hand-edit

`src/bindings/*.ts` is generated by `ts-rs` from the Rust DTOs
(`#[ts(export, export_to = "../frontend/src/bindings/")]`), each file
headed `// This file was generated by [ts-rs](...). Do not edit this file
manually.` Never edit these files and never run the linter/formatter's
`--fix` against them (they're excluded from both, see `.oxlintrc.json`'s
`ignorePatterns` and `.prettierignore`). If a binding type looks wrong,
fix the Rust DTO and regenerate — don't patch the generated file.

## Doc comments

TSDoc `/** ... */` used sparingly, only on non-trivial exported functions:

```ts
/**
 * Human-readable Loco error for toasts and forms.
 *
 * Prefers `errors[field][0].message`, then the first field error, then
 * `description` / `error`.
 *
 * @param error Thrown value from `fetch` helpers.
 * @param field Optional JSON field to highlight.
 * @return Display string.
 */
export function locoErrorMessage(error: unknown, field?: string): string {
```

Don't add doc comments to every trivial function/component — match the
existing sparse style.

## Tests

Vitest + React Testing Library, colocated `*.test.ts` / `*.test.tsx` next
to the source file (no separate `__tests__` tree). Use `describe`/`it`/
`it.each` for table-driven cases:

```ts
describe("safeRedirectPath", () => {
  it.each([undefined, null, 123, "https://example.com"])(
    "rejects unsafe or looping redirect %s",
    (candidate) => {
      expect(safeRedirectPath(candidate)).toBe("/dashboard");
    },
  );
});
```

Be aware of `src/test/setup.ts`'s global behavior before writing
assertions: it resets `localStorage`, resets i18n to `"en"`, stubs
`matchMedia`, runs RTL `cleanup()`, and dismisses toasts — all before/after
each test. `vitest.config.ts` sets `restoreMocks: true`, so mocks/spies
are auto-restored between tests; no need for a manual
`vi.restoreAllMocks()` in `afterEach`.

## Tooling note: oxlint, not ESLint

Linting is `oxlint` (config: `frontend/.oxlintrc.json`), not
ESLint/typescript-eslint. Reason: this project's `typescript` is `^7` (the
new native Go compiler), which `typescript-eslint` does not support as of
this writing (it hard-throws on import — tracked in
[typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940),
blocked on TS 7.1's programmatic API). `oxlint` + `oxlint-tsgolint` is
built directly on `tsgo` (TS 7's compiler), so type-aware linting
(`options.typeAware: true` in the config) works natively against this
project's real TypeScript version — no shim needed.

Known gap: oxlint has no `import/order`-equivalent rule yet, so import
ordering isn't enforced by tooling. Don't reintroduce ESLint/
typescript-eslint just to get it back — that reintroduces the TS 7
incompatibility this setup avoids.

oxlint's `react` plugin bundles the same React Compiler-oriented rules as
`eslint-plugin-react-hooks@7` (`set-state-in-effect`, `refs`, ...); they're
off in `.oxlintrc.json` for the same reason described for
`react-hooks/exhaustive-deps` above — adopting them is a deliberate future
decision, not a side effect of linting.
